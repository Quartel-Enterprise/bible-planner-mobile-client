PR #386 (2.8.0) gates every `Synchronizer.observeRealtime` behind `AppForegroundStateHolder` (core/model, fed by ON_START/ON_STOP in `AppRoot.kt`, collected in `SyncCoordinator`). Reason: supabase-kt (still in 3.8.0) launches `setAuth` in its own unsupervised scope on session refresh whenever `Realtime.status == CONNECTED`; anything thrown there (`websocket` getter → "Websocket not yet initialized", `checkAccessToken` → TokenExpiredException r40) crashes the app and cannot be caught app-side. With no subscribed channels the socket disconnects (`disconnectOnNoSubscriptions`), so the listener never runs in background; missed changes are covered by the snapshot pull on the reconnect CONNECTED transition. Related: [[project-spontaneous-logout-2-0-0]].

Regression (Oct/2026 investigation, issue 20238338888878bbc6bf9b7e0cbc6c4c): 2.8.4/2.8.5 events are a different variant, `sendHeartbeat` → `websocket` getter. supabase-kt 3.8.0 `disconnect()` nulls `_websocket` before cancelling `heartbeatJob`, and a tick already running on another thread throws (no handler in the scope). Upstream fix supabase-kt PR #1395 (issue #1394) merged 2026-09-23 but unreleased as of 2026-10-04 (3.8.0 still latest): bump when the next release ships. Separate app-visible bug found: our 10 RemoteStores call `removeChannel` concurrently on ON_STOP, and more than one can see `subscriptions.isEmpty()`. Each schedules a deferred disconnect (2×heartbeat = 20s), but `disconnectJob` keeps only the last, so `addChannel` on ON_START can't cancel the orphans. A stale one then disconnects in FOREGROUND under live channels: realtime silently dies and it's another chance to hit the heartbeat race. Reproduced 1/200 with a noop websocket. The fix is to serialize removal (Mutex). "Await DISCONNECTED" can't help because the race is internal to the library.

Crashlytics triage (Aug 2026, all open fatal Android issues resolved): NoSuchMethodError issues 7c080f7c (WorkManager `JobScheduler34.forNamespace`) and 31fdcf9b (`WindowInsets.Type.systemOverlays`) are MUTED — devices reporting SDK 34 with pre-release/modified Android 14 frameworks missing API-34 methods (same installation UUID in both samples); androidx calls them unguarded even at androidx-main, so no app-side fix or bump helps.
